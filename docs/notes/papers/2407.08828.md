## Definitions and cautions (PDF p. 1-5)

- [P] A benchmark is (i) a set of tasks with a procedure for running them and (ii) a method for computing performance
  metrics from the classical data. No single benchmark or metric captures all aspects of performance. (PDF p. 2-3)
- [P] Benchmarks exert "sociological forces": they steer calibration choices and funding, so optimizing a system on a
  benchmark that does not summarize all important performance aspects "can easily lead to unproductive choices"; the
  example is calibrating a many-qubit system with one- and two-qubit RB, which is insensitive to crosstalk. (PDF p. 3-4)
- [P] Six desirable properties, offered as ideals and not binary tests (PDF p. 4):
  1. well-motivated metrics;
  2. well-defined, with any unspecified step an intentional configurable parameter;
  3. implementation-robust: configurable parameters cannot be exploited to obtain misleading results;
  4. system-robust: results survive a priori unknown small errors of the tested machine;
  5. efficient in quantum and classical resources;
  6. technology independent except where the metric is technology specific.
- [P] The accepted robustness standard proves accuracy for small Markovian errors; qubits "often experience significant
  non-Markovian errors" that corrupt benchmarks (leakage corrupts RB), and theories for general errors are only
  beginning. (PDF p. 4-5)
- [P] Metrics a benchmark defines for itself (quantum volume) make robustness hard to assess; algorithm-based benchmarks
  "typically meant to quantify how well a system can run interesting instances ... do not necessarily do so".
  (PDF p. 5)

## Errors and compilation (Box 1, Box 3; PDF p. 2, 7)

- [P] Under independent flips at rate epsilon per location the probability of at least one error in a width-w, depth-d
  circuit is 1 - (1-epsilon)^(wd), about w d epsilon, so success requires epsilon much smaller than 1/(wd). Real devices
  show coherent and stochastic Pauli errors, crosstalk and slow drifts, so one error rate is insufficient. (Box 1,
  PDF p. 2)
- [P] What a benchmark measures depends on the compilation it permits. Standard RB works only if compilation barriers
  keep sequential Cliffords uncompiled together. A benchmark that allows replacement of a circuit by any circuit with the
  same output distribution "can be gamed": a classical compiler can replace C by a trivial circuit that encodes the
  precomputed output whenever C is classically simulable. (Box 3, PDF p. 7)
- [P] A classically tractable problem (factor 15) can be solved using mostly classical resources; the Shor-based
  factorings of 15 used a compilation possible only because the factors were known. A good benchmark restricts the
  classical computation allowed. (PDF p. 7)

## Error mitigation and verification (PDF p. 7-8, Box 4)

- [P] "The results of benchmarks run with error mitigation should currently be interpreted with extreme caution",
  because no clear connection has been made between error-mitigated performance and progress toward quantum utility.
  (PDF p. 7)
- [P] Low-level program benchmarks forbid intrusive compilation, so they can expose unexpected qubit and gate errors by
  comparing observed performance with a model; high-level program benchmarks mix classical and quantum performance and
  "can easily mislead" when used to compare machines. (PDF p. 7-8)
- [P] Verification problem: computing the error-free distribution of a circuit costs exponential time in general, so
  benchmarks use efficiently simulable circuits or "output modifiers" that replace circuits by simulable proxies of
  provably similar performance; some verification methods "make strong assumptions about the nature of a quantum
  computer's errors". (Box 4, PDF p. 8)
- [P] Tomography-derived metrics are data intensive and rarely used beyond two qubits; worst-case metrics (diamond norm)
  are rarely reported because they are pessimistic and hard to measure. (PDF p. 9)

## Utility, resource estimates, capability (PDF p. 9-12)

- [P] Progress claims need a challenge problem, a resource estimate and a roadmap; a classically hard problem is a
  moving target because classical algorithms improve, "even a 1000x quantum advantage could be erased within years (or
  even days ...)". Existing resource estimates rest on oversimplified single-error-rate models. (PDF p. 9-10)
- [P] Component benchmarks alone do not reliably predict emergent behavior; the authors favor multidimensional
  capability regions over a single scalar. (PDF p. 11-12)
